# 53. Streaming import: two passes, compact notes, bounded memory

- Status: Accepted
- Date: 2026-10-18
- Amends: ADR 0017 (the file limit is 2 GiB, the archive is read from its file, the apply reads the file again and keeps the plan's decisions as a digest; the merge rules and checks are unchanged), ADR 0025 rows 7 and 9 (zip64 end records are read; the memory budget is 200 MiB, measured differently), ADR 0018 (the plan holds a fingerprint of the file, not its content)
- Refers to: SPEC §4.1 "Streaming import", `docs/briefs/phase-2.md` (slice 1)

## Context

`plan_import` read the whole archive into memory, then the decompressed `cards.json`, then parsed it into one document, which the plan kept until the apply (ADR 0025 row 9: about 3.7 bytes per byte of JSON, a 1 GiB budget at the 256 MiB limit). Phase 2 adds images and audio to the archive (`media/`), so an archive can be far larger than its JSON: it cannot be held in memory, and the plan cannot hold the document while a dialog is open.

The brief asks: peak memory under 200 MiB for any file the import accepts; the archive up to 2 GiB, an image up to 10 MB and an audio file up to 20 MB; the checks, merge rules and summary unchanged; a refused file still writes nothing; and an archive reader that a later slice can extend with media entries.

## Decision

**Read from the file, entry by entry.** `Archive::open` takes the file (a `BufReader<File>` behind a `Window` that cuts it to the size checked against the limit, so nothing past it is read even if the file grows). It reads the end record first, which must end the file, and refuses, before anything else is read, more than 100,000 entries or a central directory over 16 MiB, and a directory that does not end before the end records. **The archive is read by our own code, not the `zip` crate's reader** (the crate still writes exports): that reader keeps every central record with its name and comment in memory whatever size the end record declares, and when one end record does not work out it tries every earlier one it finds, each with its own count, so a crafted 131 MB file took 389 MiB, one with a zip64 end record hidden behind the last one 376 MiB, and 400 end records after a damaged directory 1.4 s for a 3 MB file (gigabytes and days at 2 GiB). Our reader walks the central directory the last end record names, record by record: exactly the declared number of records, which must fill exactly the declared size; each name is compared at once with the names Rappel writes and the first other name refuses the file, so no name or comment is kept, and the walk reads at most 16 MiB with a fixed buffer. Each entry gets a role (`cards.json`, `media/`, and in slice 2 `media/<sha256>.<ext>`). Every check of ADR 0017 and 0025 stays and covers N entries: a name used twice, supported methods (Stored, Deflate) without encryption, the right kind, and entries that do not overlap (from their local headers; sorted by start, each ends before the next starts) and end before the central directory. Bytes before the archive are not looked for: offsets are taken as they are. An entry's data is read by `open_entry`: Stored, or Deflate through `flate2`, its bytes counted against a hard cap (one byte past it fails, whatever the entry declares), hashed with SHA-256, and at their end checked against the central record's CRC and size; `copy_entry` streams one to a writer that way, for slice 2's media. Nothing is extracted.

**zip64 end records are read.** Over 65,534 entries, the zip format needs a zip64 end record, and the zip crate writes one. It is accepted only exactly where the writer puts it: the 56-byte record (no extensible data, one disk) just before its 20-byte locator, just before the classic record, whose fields are each either the zip64 marker or the same value. The count, the directory's size and its offset come from it; no other end record is ever read. Before, any zip64 marker was refused (ADR 0025 row 7); every damaged header is still refused or harmless (the fuzz tests).

**Limits** (`interchange::Limits`): archive 2 GiB; 100,000 entries; central directory 16 MiB (100,000 central records with media names of about 122 bytes fit, with room); `cards.json` 256 MiB, unchanged; one image 10 MB and one audio file 20 MB (decimal, as GNOME shows sizes), for slice 2; card side, deck name and tag name as before.

**`cards.json` as a stream.** serde_json reads it from the entry (`Deserializer::from_reader`), and a visitor walks the top-level object key by key and each list record by record: each record is parsed with its serde type as before (so unknown fields, a missing `deleted_at` and wrong types are refused exactly as before), handed to the import's engine, and dropped. serde_json reads a string whole before handing it over, so the reader under it follows the strings of the text (open, escaped, length) and refuses one longer than any field can be: six times the longest text limit (a card side with every character written as `\u00XX`), 6 MiB. That is a new refusal (`Json`, "a string longer than … bytes at line …, column …"), for files no export can be; before, such a string was read, then refused for its field or its type.

**Compact notes instead of rows.** What the checks need across rows is kept as numbers (`interchange::notes`):
- ids as their 122-bit values (`id::uuid_v7_value`; equal exactly when the strings are, ordered as they are), in vectors sorted once their table is read and searched by bisection: decks (with a bit for deleted), cards, tags, and per log entry 32 bytes (id, time and kind, its card as a position, its row);
- names (live deck name keys, tag name keys) as 64-bit digests;
- per undo, its id and the key of the entry it names (32 bytes).

A value that appears twice in its sorted vector is only a candidate: the table is then read again (`Locate`) with every row checked in order and only the candidates tracked, in memory fixed by their number (a flag per candidate id or undo target, and per candidate name digest the 128-bit hash of the first name seen with it, so names that only share 64 bits are told apart; a set of the names themselves took 292 MiB for 2 million repeated tag names). That finds the first problem in row order as a set of every value did (two different names sharing all 128 bits, a chance of 2^-127, would be taken for one), and finds nothing when two names only share a digest. Card tags keep no notes (they must be sorted, ADR 0025 row 9). The undo checks run once the log is read, over the notes, and report the first failing undo by row. Everything else is checked as the row goes by, with the same functions in the same order as before (`validate`), so the first broken rule of a row is the one reported.

The notes are what grows with the file: measured, about 0.4 bytes per byte of JSON for the worst rows (tags: two notes in each 57-byte row), so the 256 MiB JSON limit stays: far above real collections (about 1.7 million review events), and within the budget with compact notes.

**Nesting is bounded too.** serde_json skips a value it does not need (the fields of another version, read before the version is known) without a depth limit, keeping a byte per level: 200 Mi `[` took 206 MiB. The reader under it also counts how deeply arrays and objects are nested outside strings, and refuses past 1,024 levels (`Json`, "nested deeper than 1024 levels at line …"); serde_json already refuses more than 128 wherever it parses a value, and an export has 4.

**One pass for an export, step by step otherwise.** An export writes `format_version` first and the lists in file order. Such a file is read in one pass: each row checked and compared with the database as it comes. Anything else (a problem, a candidate duplicate, the keys in another order, which serde has always accepted) is read again one step at a time, in the order the checks have always come: the entry (its size, its CRC) and `format_version` alone (`Header`, as before), the shape of the whole document (every record parsed, nothing kept: the JSON errors), `exported_at` and `media`, each list on its own read, the settings last; and only once all of that passed, each list once more, compared with the database (and written, when applying). So a file refused there costs no query. That finds exactly the problem the old reader found, at the same line (and the same column or the next: a streaming parser counts the byte it peeked at), and reads any valid file whatever its key order, at the cost of up to twelve reads.

**The plan compares as before, row by row.** As a row goes by, it is compared with the database by its id (new, present, revived or a conflict, ADR 0017), with the record in hand, so no record needs keeping or digesting. The cards deleted with a revived deck are found once the cards are read; deck name conflicts are listed after all others, as before; the settings decision is taken against the stored settings and "has decks" read before anything else. Each decision goes, in order, into a SHA-256 digest (table, row, decision, and the stamp or database id it depends on). `ImportPlan` holds the summary, that digest, how the file was read, its limits, and a fingerprint of the file: its size, modification time, device and inode when it was opened, and the SHA-256 of `cards.json` computed while it streamed. Nothing of the content; a plan is a few hundred bytes. It is `Send`, so the app's workers are unchanged.

**The apply reads the file again.** If the plan has conflicts or nothing to do, nothing happens, as before. Else the file is opened again and must have the same stamp (else `Error::ImportFileChanged`, before anything is written); the database is backed up; then, in one `IMMEDIATE` transaction, the same engine reads the file the same way, compares each row again with the database as it is now, and writes it at once (decks and cards inserted or revived, the cards deleted with a revived deck after the cards, tags, card tags, log entries). Undos are written after the whole log, in id order, so the entry each cancels is always there first, whatever the file's order. Then: the digest and the summary must equal the plan's (else `ImportPlanStale`: the database changed since, as `concurrent.rs` tests), and every read must give the plan's SHA-256 of `cards.json` (else `ImportFileChanged`: a change the stamp missed, such as other content of the same length with its time put back). Only then are the settings replaced (if applied) and the schedules of the cards that got entries rebuilt, and the transaction committed. Any error drops the transaction, so a refused or changed file writes nothing. A changed file found by its hash comes after the backup, which only adds a backup.

**Errors.** New: `ImportProblem::TooManyEntries { limit }`, `Error::ImportFileChanged` (the app says "The file changed since it was checked. Nothing was imported; import it again.", or while checking, "The file changed while it was being checked. Import it again."). `InvalidArchive` also says when the list of entries is too large.

**Dependencies.** `sha2` 0.11 (MIT OR Apache-2.0, already in the tree through `rust-embed` for the app's fonts), for the hash of `cards.json`; slice 2 names media files by it. It is built optimised in debug builds too (`[profile.dev.package.sha2]`), since it runs over every byte an import reads. `flate2` 1.1 with the `zlib-rs` backend (MIT OR Apache-2.0; zlib-rs is Zlib) and `crc32fast` 1.5 (MIT OR Apache-2.0), both already in the tree through `zip`, which used them for us before: the archive reader inflates and checks CRCs itself now.

## Consequences

- Memory, measured in `tests/import_memory.rs`, each case in a process of its own. The JSON cases are measured at two sizes and extrapolated along the line through them to 256 MiB of JSON, which is an approximation: what grows with the file (the notes) grows linearly, and the fixed costs are counted once, but a case is not run at the limit itself. Budget 200 MiB: planning review events about 38 MiB at the limit, resets and undos 51, tags 95, decks 44, a refused file of repeated tag names (the second read that confirms them) 130, card tags and long cards about 1; planning and applying resets and undos 103, tags 142 (the apply's slope includes SQLite's page cache filling, so these overestimate). The hostile archives are measured as they are, each refused with a peak under 1 MiB: a billion entries declared, a list of entries declared nearly 4 GiB long, a file over 2 GiB, 100,000 entries (a zip64 end record), central records with 64 KiB comments behind a lying size, 400 end records after a damaged directory, a zip64 end record with a million entries behind the last end record, and 16 million levels of nesting. With the reviewer's own files at full size (131 MB of comments, 138 MB behind a hidden zip64 record, 200 Mi levels of nesting, 2 million repeated tag names in 128 MB of JSON), the whole process peaked at about 6 MiB for the archives (refused in under 0.1 ms) and the nesting (0.24 s), and 118 MiB for the repeated names. Before: up to 948 MiB for valid files, 389 MiB for a 131 MB crafted one.
- Time, for a file as an export writes it (release build): planning 27 MiB of JSON with 120,000 rows takes 158 ms instead of 123 (serde_json reading from a stream is slower than from a slice, and the hash and the string check cost a few percent); planning the 5,000-card export 15 ms instead of 10; planning and applying the 20,000-entry log 235 ms instead of 169 (the apply now parses the file again). Long card sides cost the most: about 2.5 times as long, 85 ms for 32 MiB. A file in another key order is read up to twelve times. In the debug test build the 5,000-card plan takes 160 ms instead of 88, and the long-log import 1.1 s instead of 0.61. A refused file can be slow when it has millions of rows: the one pass compares its rows with the database before it finds the problem at the end of a list (2 million repeated tag names: 14.5 s, most of it the queries of the one pass).
- A file whose key order is not an export's is still accepted, and gives the same summary and refusals as before: the property tests compare with the old reader, kept as a test oracle in `interchange/tests/oracle.rs`, and for every accepted file without conflicts they also apply it with the old code on a copy of the database and compare the two databases (export and schedules). A file changed between two reads of one plan is refused as changed (a test changes it before each of the twelve reads). A top-level array (which serde also took for the document) is still refused, as it always was in practice: reading the version alone refuses any array but a one-item one, which the document's own read refuses for its length.
- The apply takes as long again as the plan for the reading, on top of the writes; the backup is made before the file's content is checked again, so a file changed in a way its stamp does not show leaves one more backup.
- `media/` entries are still refused, and `media` must still be empty: no format change. Slice 2 adds a role for `media/<sha256>.<ext>` to the directory walk (checked as the name is read, so names are still never kept), and copies each with `copy_entry` and its cap; the entries the walk keeps are about 80 bytes each, 8 MB at 100,000.
- `id::is_uuid_v7` and `uuid_v7_ms` are test-only now; `parse_id` no longer allocates.

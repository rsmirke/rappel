# 52. A damaged setting can be reset, a restore keeps a waiting copy, and tag suggestions offer used tags only

- Status: Accepted
- Date: 2026-10-18
- Amends: ADR 0050 row 37 (a damaged stored setting no longer stops the app with no way on), ADR 0050 row 35 and ADR 0007 (a restore no longer replaces a waiting restore copy), ADR 0029 (tags are still never deleted, but unused ones are no longer offered), ADR 0051 (the Add Tags dialog's suggestions)
- Refers to: ADR 0026 (backups), ADR 0027 (settings), `docs/briefs/phase-2.md` (slice 0), `docs/briefs/QUESTIONS.md` notes 2, 3 and 5

## Context

Phase 1's batch mode left three questions for the maintainer (QUESTIONS.md notes 2, 3, 5). The Phase 2 brief answers them, and pre-approves the one overwrite this needs: resetting a damaged setting, after a backup.

1. A value in the `settings` table outside its range (a hand edit, a damaged file) was refused by every read, so the first one, the deck list's, failed and the window showed "Rappel Could Not Start / The decks could not be read" with the error and nothing to do (ADR 0050 row 37). Whether the user saw it depended on which read came first.
2. Restoring a backup renamed its checked copy over `rappel.sqlite3.restore.partial`, so a copy an interrupted restore had left waiting was replaced (ADR 0007; "Noted, not changed" in ADR 0050 row 35). That copy is the user's data.
3. Tags are never deleted (ADR 0029), so a typo tag added and then taken off stayed in the suggestions of the card editor and of Add Tags, and in the All Cards tag filter, forever.

## Decision

**1. A damaged stored setting.**
- **Core detects it at open, by key.** `Store::open` gets a sixth step: after the migrations it reads the stored settings, and a value that is not valid for its key stops the open with the new `Error::DamagedSetting { key, value }`. `key` is a `SettingKey` (`DesiredRetention`, `MaxNewPerDay`, `MaxReviewsPerDay`, `DayStartHour`), one of the known keys, never the file's text; `value` is the start of the stored text (at most 64 characters, as before), for the log only. Every other read of the settings (`settings_in`, `stored_settings`, the scheduler, export) returns the same error instead of `InvalidColumn`, so nothing ever runs with a bad value, and an open store never has one. The keys are checked in `SettingKey::ALL` order, so the first damaged one is named.
- **The check runs after the migrations**, on the current schema, so the reset needs no knowledge of older ones. No migration reads the settings today: only 0002 and 0005 rebuild the schedule, before the settings table (0006) exists. A test (`no_migration_reads_the_settings`) fails if a later migration rebuilds the schedule, so whoever writes one handles a damaged value first.
- **`storage::reset_setting(data_dir, key)`**, an associated function like the recovery ones: it opens the database as `Store::open` does without the settings check, and only if `key`'s stored value is still damaged makes a backup with the online backup API (into `backups/`, as before a migration; if it fails, nothing is changed and its error is returned), then in one transaction deletes that one row, so the default applies. For the desired retention the whole schedule cache is rebuilt with the default retention in the same transaction, as `set_desired_retention` does. The row is checked again inside the transaction. Then the settings are checked again. It returns a `SettingReset`: `was_reset` (false if the value was readable again, which leaves it alone with no backup) and `then`, either `AfterReset::Opened(store)` or `AfterReset::Damaged(next)` for a second damaged key. No other setting, card, tag or log entry is touched. Deleting the row rather than writing the default keeps the "a key never written has its default" rule (ADR 0027): an export of the reset database does not carry a setting the user never chose.
- **The app's page.** `startup::open_problem` maps `DamagedSetting` to `Problem::DamagedSetting { key, data_dir }`, which the window shows as its own page (`SettingPage`, `data/setting_page.blp`): "A Setting Is Damaged", a description that names the setting as Preferences does ("Desired Retention", "New Cards per Day", "Reviews per Day", "Day Starts At"), says Rappel did not open the database, that a backup is made first and what the default is ("90%", "20", "200", "04:00"), a suggested-action pill **Reset This Setting** with the focus, and the data folder line. The reset runs on a worker (`ui::worker`) with a spinner and the button disabled. On success the main page shows with the toast "“Desired Retention” was reset to 90%. A backup was made first." (or, if core found the value readable again, "“Desired Retention” can be read again, so it was not changed."). If another setting is damaged, the page shows that one, with that toast for the first. The page's title is in the Blueprint only. A failure is an error toast through the page's `ErrorSlot`, and the page stays. No confirmation dialog: nothing the user can read is lost (the value cannot be read at all), and a backup is made first.
- A restore or Finish Restore whose installed database has a damaged setting has moved the files all the same, so core returns `Error::InstalledWithDamagedSetting { key, replaced, set_aside }` instead of a bare `DamagedSetting`, and the recovery page hands all of it to the window (`RecoveryPage::set_on_damaged_setting`), which shows the same page with the recovery toast that says where the old files went.
- After a startup problem page (this one, as the recovery page already did), the main page keeps the window's startup size: the saved size, maximised state and deck are applied only before the window is first shown (`restore_state`), and resizing a window the user already sees is not done. If a setting is damaged after the open (another process), the main page's first read shows the same page.

**2. A restore keeps a waiting copy.** Before `restore_backup` installs its checked copy under `rappel.sqlite3.restore.partial`, a regular file waiting there gets a second name, a free `rappel.sqlite3.restore.set-aside-YYYYMMDD-HHMMSS[-N]`, by a hard link that fails if the name is taken (then the next is tried), so nothing is ever overwritten. The restore then renames its copy over `partial`, which replaces only the name: the old file lives on under the new one. `partial` thus names a checked copy at every moment, and a crash anywhere leaves `Store::open` refusing to start an empty database (`InterruptedRestore`), as ADR 0007 requires; a retry sets the same file aside again under the next free name, a harmless duplicate. Where the file system refuses hard links (`Unsupported`, `PermissionDenied`), the waiting copy is copied byte for byte to the scratch name `rappel.sqlite3.restore.set-aside.part`, synced, and only then renamed to the free name, so a crash never leaves a cut copy under a set-aside name. Without hard links no rename refuses to overwrite, so the free name is checked just before: a file another program creates there in between could be replaced. Nothing in Rappel writes such names; the residual race is accepted. This is the hard-link and free-name code Start Fresh uses for refused copies (`link_to_free_name`, `free_name`), shared, not copied; Start Fresh still removes its old name afterwards, a restore does not need to. `Restored::set_aside` says where, and the recovery toast names it: "Backup restored. The previous database was kept as …. The copy an earlier restore left waiting was kept as …", the same sentence Start Fresh now uses. Anything but a regular file at the copy's name is left alone and the restore is refused (an `AlreadyExists` IO error, the scratch copy removed, nothing changed); before, a folder made the final rename fail and a symbolic link was replaced. Nothing is deleted.

**3. Tag suggestions offer used tags only.** `Store::used_tags()` is one query: the tags linked to at least one live card (not deleted, in a deck that is not deleted; a suspended card counts), in name-key order. The card editor's `TagEntry` and the All Cards Add Tags dialog take their suggestions from it. The All Cards tag filter lists the same tags, since filtering by an unused one can only give no cards, except that the tag chosen in the filter stays listed when it falls out of use (`text::filter_tags`), so a choice never vanishes under the user; the filter is read again after every bulk write and its Undo. A tag that comes back into use (an Undo, an undelete) is offered again. No tag is deleted: `Store::tags()` still lists them all, and export carries them all (deleting unused tags would be a data change for the maintainer to decide).

## Consequences

- QUESTIONS.md notes 2, 3 and 5 are done. ADR 0050 row 37's "no way on" and row 35's "Noted, not changed" no longer hold.
- `rappel-core`'s API: `Error::DamagedSetting`, `Error::InstalledWithDamagedSetting`, `domain::SettingKey`, `storage::reset_setting` with `SettingReset` / `AfterReset`, `Store::used_tags`. `Error::InvalidSetting` keeps its `&'static str` key (it is a setter's refusal); `InvalidColumn` is no longer used for settings.
- Each reset adds one backup; the next open prunes by ADR 0026's rule. A restore past a waiting copy leaves one more file in the data folder.
- The app gets `rusqlite` as a dev-dependency only (already in the workspace, same version and licence): its tests write a damaged value as a hand edit would. The app itself still never reaches SQL.
- No migration, no export-format change.

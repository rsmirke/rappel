# 54. The media store: content-addressed files, references, export and import

- Status: Accepted
- Date: 2026-10-18
- Amends: ADR 0017 (an export holds the media files and their records; `media` is no longer always empty), ADR 0019 (a `media:` image target is a checked reference; a link to an audio file is an audio inline), ADR 0053 (the archive reader accepts `media/<sha256>.<ext>` entries), ADR 0025 and ADR 0050 (rows 39 to 41 of the untrusted-input table)
- Refers to: SPEC §3 (`media` table), §4.1, §4.3, §4.9, principle 5; `docs/briefs/phase-2.md` (slice 2)

## Context

Phase 2 brings images (slice 3) and audio (slice 4) to cards. Both need the same core first: where the files live, how a card names one, how they travel in an export and come back in an import, and what is accepted. The file content is untrusted (pasted, dropped, imported), so it must never be taken for something else (SVG with a script, HTML), never name a path, and never cause network access (principle 5). The streaming import of ADR 0053 left the place for media entries in the archive reader, with caps of 10 MB per image and 20 MB per audio file.

## Decision

**Kinds, from the first bytes only** (`media::MediaKind`). A file's kind is its magic number, never its name or a declared type: a JPEG called `x.png` is a JPEG and is stored as `.jpg`. Each kind has one extension and one MIME type, the only ones written and read:

| Kind | Signature checked | Extension | MIME | Limit |
|---|---|---|---|---|
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `png` | `image/png` | 10 MB |
| JPEG | `FF D8 FF` | `jpg` | `image/jpeg` | 10 MB |
| WebP | `RIFF` …. `WEBP` | `webp` | `image/webp` | 10 MB |
| GIF | `GIF87a` / `GIF89a` | `gif` | `image/gif` | 10 MB |
| Ogg | `OggS`, version 0, beginning of stream, first packet `OpusHead` or `\x01vorbis` | `ogg` | `audio/ogg` | 20 MB |
| MP3 | `ID3` (version 2 to 4), or a layer III frame header with a valid version, bit rate and sample rate | `mp3` | `audio/mpeg` | 20 MB |
| M4A | `ftyp` box whose major or a compatible brand is `M4A ` or `M4B ` | `m4a` | `audio/mp4` | 20 MB |
| WAV | `RIFF` …. `WAVE` | `wav` | `audio/wav` | 20 MB |

Only the signature is checked: a truncated or damaged file of a kind is that kind here, and the decoders of slices 3 and 4 find the damage. Anything else is refused (`MediaProblem::NotMedia`): SVG, HTML, XML, PDF, AVI, video MP4 (`isom`, `mp42` without an audio brand), Ogg Theora. An empty file is refused (`Empty`), and so is one past its kind's limit (`TooLarge`), counted while it is copied. **Ogg: Opus and Vorbis both**, not only Opus as the brief says: GStreamer plays both, Vorbis is the older common Ogg audio, and telling them apart costs nothing; any other Ogg codec (video, FLAC, Speex) is refused. A file that is a valid signature followed by HTML or script (a polyglot) is accepted as that kind: its bytes only ever go to a decoder of that kind, never to anything that reads HTML or runs code.

**Storage** (`media/store.rs`): `<data dir>/media/<sha256>.<ext>`, the folder mode `0700` (made with the first file), files `0600`. `Store::add_media(reader)` (and `add_media_bytes`) streams the input into a new temporary file in the folder (`.incoming-<random>`, `create_new`, so never through a link or onto an existing file), reads the kind from the first 512 bytes, caps the copy at that kind's limit, hashes as it goes, syncs, then gives the file its name with a **hard link, which never replaces a file**: if the name exists, that file is hashed (at most 20 MB, read once) and kept if it has the same content; a file with other content (of the same size or not) is damaged, so it first keeps a second name (`<name>.damaged-<random>`, logged; a hard link, or where links are refused a copy to a new file) and only then does the good copy take the name, so nothing is replaced and nothing lost; anything that is not a regular file there refuses the add. Where hard links are refused (some file systems), a rename after checking the name is free. The linking calls go through a small `Namer` trait so tests can take hard links away. Then the folder is synced and the row inserted (`ON CONFLICT DO NOTHING`, so the first `created_at` stays). The temporary name is removed in every case; a crash can leave one, never under a media name. `MediaRef` (hash and kind) gives the reference `media:<sha256>.<ext>` and `Store::media_path`, the only way to a path: built from a checked hash and a fixed extension inside the media folder, never from card text. **In-memory test stores have no media folder** (`Error::NoMediaDir`), like their missing backup folder; tests of media use a temporary data directory.

**Migration 0011** adds `media(hash, mime, bytes, created_at)` (SPEC §3) as a STRICT table with CHECKs: 64 lowercase hex digits, a MIME type of the table above, `bytes > 0`. Nothing references it: cards name files in their Markdown. Another kind will need a migration that rebuilds the table with a wider CHECK (nothing references it, so it can be rebuilt with foreign keys on).

**References in card Markdown** (`content`, ADR 0019 amended). `MediaRef::parse` accepts exactly `media:` + 64 lowercase hex digits + `.` + a canonical extension; upper-case hex, another extension, a path, a query or anything more is not a reference. An image whose target is a reference to an image kind is `ImageTarget::Media(MediaRef)`; a link whose target is a reference to an audio kind is the new `Inline::Audio { content, media }` (SPEC §4.9: `[](media:<sha256>.<ext>)`); everything else stays as before (an image shown as the Markdown typed, a link with its URL as tooltip, never opened). The app shows `[image: …]` and `[audio: …]` placeholders until slices 3 and 4. `content::media_refs(md)` lists the files a side names, each once, in order: every valid reference in an image or link target, whatever its kind (an audio file as an image target, shown as text, still counts), so a file a card names counts as used for slice 5. It follows the parsed tree, so it is bounded as `parse` is (20,000 references, 10,000 levels of nesting and 50,000 brackets are listed in a time bound on a small stack), and an image flattened past the nesting cap (ADR 0019) is not a reference, as it is not shown.

**Export** (ADR 0017 amended). `cards.json`'s `media` list has one record per row of the `media` table: `hash`, `mime`, `bytes`, `created_at`, in that order, sorted by hash. **Every row, not only the files cards name**: it is simpler, and a file that only a deleted or trashed card names stays restorable; deciding what is unused is slice 5's design. The archive holds, after `cards.json` and `media/`, one entry `media/<sha256>.<ext>` per record, sorted by name (which is by hash), **Stored**: the formats are compressed already (WAV is the exception, and rare), storing is deterministic whatever the Deflate implementation, and costs no CPU. The files are streamed from the media folder into the archive, which is written straight into the export's temporary file (`ArchiveWriter` over a `BufWriter<File>`), so no file is ever held in memory. **A file that is missing or damaged** (not a regular file, or not the size, kind or hash its row records, or a row whose hash or type Rappel cannot name, which only a damaged database has) is left out with its record and counted in `ExportSummary::missing_media`; the app's toast says how many and stays until dismissed. Refusing the export would leave the user with no export at all for a loss that already happened; writing the record without the file would make the export unimportable. To know before writing an entry, each file is read once to check it and again to copy it (hashed again: a file that changed in between fails the export, since the entry is written already).

**Import.** The records are read with the rest of `cards.json` (unknown fields denied, like every record) and checked as they stream by, in order: the hash (64 lowercase hex digits), then sorted by hash and each once (as `card_tags` must be sorted, ADR 0025 row 9, so no set is kept), the MIME type (of the table), the size (above 0, within the kind's limit) and `created_at`. A note is kept per record (hash, kind, size, time: 56 bytes), at most as many as the archive has media entries; past that a record cannot have a file, which refuses the file anyway. These checks come with the top level, right after `exported_at`. Then, before any list rule, each record must have exactly one entry `media/<hash>.<ext>` with its type's extension and its size, and each media entry a record (names compared as bytes; the first mismatch in hash order is reported: `NoMediaFile`, `SizeDiffers`, or the entry named as unexpected). After every other check passes, **the plan reads every media entry once, writing it nowhere**: through the archive reader's cap and CRC check, its first bytes must be of the record's type (`NotOfItsType`) and its SHA-256 the record's hash (`MediaFileDiffers`). So a file whose media lie is refused before anything is written. Each record is then compared with the database by hash: new, present (the same type and size; `created_at` may differ and the database keeps its own), or a conflict (`Conflict::MediaDiffers`: another type or size under the same hash, which only a damaged database can have); the decisions go into the plan's digest. The summary counts them (`ImportSummary::media`), and media alone are something to import.

**Apply**: after the backup, inside the transaction, once the file read again gives the plan's decisions, each new file is streamed from the archive into the media folder by the same code as `add_media` (hashed and checked again, each file synced, the folder synced once at the end) and its row inserted with the record's `created_at`, before the commit. A file that is not the plan's (another hash, kind or size, a damaged entry) is `Error::ImportFileChanged`, and the transaction is dropped. Files written before such a failure stay in the folder under their own hash, unused: content-addressed files are harmless, nothing in this slice deletes a file, and slice 5 removes unused ones. Files the database already has are not read again.

**A card may name a file that is in neither the file nor the database**: accepted. SPEC never required references to resolve, an export made after a file was lost leaves it out (above), and refusing would make such exports unimportable; the editor and the review page show a missing file as missing (slices 3, 4).

**Archive reader** (ADR 0053 amended). The central directory walk gives each name a role at once: `cards.json`, `media/`, or `media/<sha256>.<ext>` parsed as above (anything else refuses the file: paths, `..`, a second slash, upper-case hex, other extensions, a NUL). A media entry must be Stored or Deflate, not encrypted, declare more than 0 bytes and at most its kind's limit (refused from the record, before anything is read). `cards.json` and `media/` twice are found as the walk goes; media names twice (or one hash under two extensions) by sorting the media entries by hash after the walk, so 100,000 entries cost a sort, not a quadratic scan. The bounds stay: the entry count and the directory size from the end record, the fixed buffers of the walk, entries that do not overlap and end before the directory. A forward seek of at most 32 KiB reads past the bytes instead of seeking, so the local headers of 100,000 small entries, a few bytes apart, are read without emptying the read buffer each time.

**Backups and restore.** Backups copy only the database. Media files are never deleted (until slice 5's trash), so the references of a restored backup still resolve, and a file added after the backup stays in the folder, unused by it.

**Never the network.** `media:` is only ever turned into a file of the media folder; no URL in card text is fetched or opened, whatever its scheme.

### Untrusted input (continues ADR 0050)

| # | Where it comes in | Risk | Status | Test |
|---|---|---|---|---|
| 39 | **A file added as media** (`add_media`, later pasted, dropped or chosen in the editor). | A script or markup taken for an image (SVG, HTML, polyglots); a huge file; a name that is a path; overwriting a file; a symlink planted in the folder. | **New.** Kind from the signature only, eight kinds, nothing else; empty refused; capped at its kind's limit while copied; named only by its SHA-256 and the kind's extension; a new temporary file (`create_new`), then a hard link that never replaces; a file already under the name is hashed, kept if it is the same content, else kept under a second name before the good copy takes the name (also without hard links); a folder or link there refuses the add. | `media::tests::*` (each kind, hostile signatures, limits, a failing reader, an existing file of the same content and damaged files of the same and of another size, a file system without hard links, a folder under the name, the table's CHECKs) |
| 40 | **Media entries of an imported archive.** | Many entries; names with paths, `..`, upper-case hex, other extensions; the same file twice; a size that lies; a bomb; content that is not its name's hash or its record's type; entries without records and records without entries. | **New.** Names parsed in the directory walk (anything else refused, never kept); at most 100,000 entries; declared sizes within the kind's limit, the read capped there whatever is declared; duplicates by sorting; every entry read once, before anything is written, and its hash and type checked; the apply hashes again. ## Consequences

- The export format is unchanged in shape (version 2): `media` lists records and `media/` holds files. An export with media cannot be imported by 0.2.0 (it refused any media). Exports without media are byte for byte what they were.
- `ImportProblem::UnsupportedMedia` is gone; new `FieldProblem`s (`NotHash`, `UnknownMediaType`, `TooLarge`, `NoMediaFile`, `SizeDiffers`, `MediaFileDiffers`, `NotOfItsType`), `Conflict::MediaDiffers`, `ImportSummary::media`, `ImportReport::media`, `ExportSummary::{media, missing_media}`, `Error::{MediaRefused, MediaRead, NoMediaDir}`.
- An export reads each media file twice; an import's plan reads each once and its apply each new one again. For a collection of a few hundred images this is a fraction of a second; at the 2 GiB archive limit it is a few seconds of reading.
- An export whose media are larger than the import's 2 GiB limit cannot be imported. Real collections are far below it; a later slice can raise the limit, which is a memory question no longer (the media are streamed).
- An apply with many new files syncs each one: about as long again as the copy on a slow disk.
- A file present in the database but lost from the folder is not restored by importing an export that has it (the database already has the row). Slice 5 can offer that.
- `fill_scratch_db --media` adds a "Media" deck: three PNGs drawn by the example itself (square, wide, tall), a one-second WAV tone, a reference to a file that is not there, and a remote image, shown as text.

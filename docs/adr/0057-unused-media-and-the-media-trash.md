# 57. Unused media: a dated trash, brought back when used again, purged after 30 days unless a backup uses it

- Status: Accepted
- Date: 2026-10-18
- Amends: ADR 0054 (media files are no longer kept forever: unused ones can be moved to a trash and purged; `add_media` names its file under the database's write lock; an import and every card write bring back the trashed files they use), ADR 0026 (a restore brings back the trashed files its backup uses), ADR 0025 and ADR 0050 (row 50 of the untrusted-input table)
- Refers to: SPEC §3 (storage rules), §4 phase 2 item 4 ("undo, restore and backups must never lose a file"), §4.8; `docs/briefs/phase-2.md` (slice 5, which pre-approves the trash flow as the only deletion of user files)

## Context

Since ADR 0054 media files are content-addressed in `<data dir>/media/<sha256>.<ext>` with a `media` row each, and nothing ever deletes one. Files pile up: an image added in the editor and not saved, an image taken out of a card, the leftovers of a failed import or a crash. The brief asks for "Clean Up Media" in Preferences, showing the space to free; unused means referenced by no card, live or deleted; unused files go to a trash folder, purged after 30 days; and a restore that needs a trashed file gets it back. This is the only place Rappel deletes a user's file, so it must be impossible for it to delete a file that the database, a backup or a restore still uses, and no crash may leave a row without its file. No migration was pre-approved for this, so the trash keeps its own times.

## Decision

**What is unused** (`media/used.rs`, `media/trash.rs`). A hash is *used* by a database when a card side names it: every card, live or deleted, in a live or deleted deck (a deleted card can be brought back by Undo, so its files must stay; that is why undeleting never needs the trash). What a side names is every reference `content::media_refs` finds (image or link targets, whatever kind; it follows the parsed tree, so a target written with an entity reference or a backslash escape counts) **plus**, to be safe, every `media:` followed by 64 lowercase hex digits anywhere in the text (in code, say): the second can only keep more. **The hash decides, not the extension**: a card naming `<hash>.jpg` keeps `<hash>.png`. Only sides containing `media` or `&` are parsed (`used::may_name_media`, and the same test in SQL for `card_hashes`): a reference can only be written with those, since CommonMark decodes entities and backslash escapes in a link target (`media\:` is `media:`) and a letter cannot be escaped. A property test checks that `card_hashes` finds exactly what parsing every side finds. A file is *unused* when it is a regular file in the media folder with a media name (`<64 lowercase hex>.<ext>`) whose hash no card names, with or without a row (a row-less one is the orphan of a failed import or a crash). A `media` row whose hash no card names is deleted with its file, or alone if its file is gone; one beside a folder or link of its name stays. **Never looked at**: `.incoming-…` temporary files (an add may be running; a crash's leftovers are not user data and are left for the user), `.damaged-…` copies (user data kept aside by ADR 0054), any other name, upper-case names, folders, links. `Store::unused_media()` counts in a read transaction (about 40 ms at 20,000 cards in a debug build; a time-bound test holds it under 500 ms).

**The trash** is `<data dir>/media-trash/<YYYY-MM-DD>/<sha256>.<ext>`, the UTC date of the clean-up; folders `0700`. If the name is taken in that day's folder (the same file cleaned up, added again and cleaned up again the same day), the next of `<date>-2` … `<date>-999` is used: nothing is ever written over, and no content needs comparing. A name in the trash that is not a real folder (a link) is skipped, never followed; a `media-trash` that is not a real folder refuses the clean-up. The dated folder is the trash's only record of time, so no table and no migration are needed: a file brought back gets a row from its name and size (the MIME type of its extension, `created_at` the time it comes back).

**Clean up** (`Store::clean_up_media`, one `BEGIN IMMEDIATE` transaction): the unused set is computed again under the write lock (the count the dialog showed is never trusted), each file is renamed into the trash after checking the name is free there (same file system; the folder is Rappel's own and every writer holds the write lock), the trash and media folders are synced, the rows are deleted, then the commit. **On any error** every moved file is moved back (newest first, only where its name is free) *while the transaction still holds the write lock* (the COMMIT is issued by hand, so a failed one leaves the transaction open), then the transaction rolls back (rows kept). **Crash windows** (each tested with injected failures): a failed rename half way puts everything back; a failure just before the commit puts everything back; a failure whose moves back fail too, or a crash between the moves and the commit, leaves files in the trash *with their rows*, and **the next `Store::open` brings back every trashed file that has a row** (`recover_rows`: it lists the trash and reads the rows' hashes once; with 5,000 trashed files and no rows, the usual case, it took about 10 ms of CPU in a debug build, so it stays on the open's path rather than waiting for the worker); a crash after the commit leaves a consistent state (rows gone, files in the trash). A power cut that loses the renames but keeps the commit leaves row-less files in the media folder, which the next clean-up takes again. **The clock.** The trash measures time by the system clock, so a clean-up is refused (`Error::ClockWrong`) when the clock is before October 2026 (when Rappel first had a clean-up) or past year 9999, behind the newest trash folder's date, or behind the newest time the database records (`latest_time`: decks and cards made, edited or deleted, log entries, media rows): its folder would then be dated earlier than the clean-up really was.

**Adding and cleaning up never interleave.** `add_media` copies, hashes and syncs into its temporary file first (a slow source never holds a lock), then takes the database's write lock (`BEGIN IMMEDIATE`) before the file gets its name and commits its row before releasing it (`ingest_then`); an import already names its files inside its own write transaction. So a clean-up never sees a file without its row (it would take the file and leave the add's row without one). Tested with two connections both ways: an add waits for a clean-up's lock before naming, and a clean-up waiting for an add's lock sees file and row together and takes both. **A file added but not yet saved in a card** (the editor is open) is unused and may be cleaned up; **every card write brings back the files its sides name** that are missing from the media folder and in the trash (`recover_refs`, inside the write's transaction; a failure is only logged, never refuses the save). So saving the editor after a clean-up keeps its images.

**Brought back** (`recover_all`): a trashed file goes back to the media folder (with a row if it has none) when the database uses it, **after its content is checked** to have the hash and kind of its name (read once, at most its kind's limit; a copy that is not is left in the trash, logged, and an older copy of the name is tried): after `restore_backup` and `finish_restore` (rows at open, then card sides), inside every `apply_import` (an imported card may name a trashed file the archive does not carry; a failure there is only logged, as for a card write, never refuses the import), and at every start on a worker (`Store::tidy_media_trash`, below). A file whose name is already in the media folder stays in the trash (it is a duplicate; the purge keeps it while the database uses it). A trash folder that cannot be read is skipped with a warning, so it never stops a restore, an import or a card write; the next start tries it again. Card writes list the trash's folders once per write.

**Undo.** The toast after a clean-up offers Undo, which puts back that toast's own clean-up (`Store::undo_clean_up`): each file still in the trash goes back unless its name is taken again, and each deleted row is written again, exactly as it was, unless its hash has a row again; a row whose file cannot go back stays deleted. It is safe after other writes for that reason.

**Purge** (`Store::tidy_media_trash`, at every start, on a worker after the main page is shown, and after a restore; logged only). First every trashed file the database uses is brought back. Then a dated folder may be purged once **the clock is 31 days past the start of its date** (so every file in it spent at least 30 days in the trash, by the clock) **and the database records a time at least 30 days past that start** (Rappel was used, and wrote, a month after the clean-up). A clock set back never purges; a clock that is ahead only at a start never purges either (nothing was written then); a folder dated before October 2026 is never purged (a wrong clock made it). **The limit, exactly:** a clock that runs ahead while the user writes (studies, edits) and at a later start can purge before 30 real days; nothing in a local app can tell. Backups still protect every file a restore could need. Its files are deleted **unless any of these uses their hash**: every backup in `backups/` (rows and card sides, read-only with `query_only`; a backup older than migration 0011 has only cards), the copy a restore left waiting (`rappel.sqlite3.restore.partial`, which `finish_restore` installs), the other database copies in the data folder (`…replaced-…`, `…set-aside-…`, `…refused-…`), and the database itself. **A backup or the waiting copy that cannot be read keeps everything** (`TrashTidied::blocked`, logged as a warning). Another copy is skipped only when it is no Rappel database at all (not an SQLite file, damaged, no `cards` table: the one a restore replaced is often the damaged database it was restored over, and must not block the purge forever); any other failure to read it (permission, IO, busy) blocks the purge too. The backups are read first without a lock; then, holding the write lock (no clean-up, add, import or card write meanwhile), the candidates are listed again, backups that appeared since are read (tested with a backup made between the two passes), the database's own use is read, and the files are deleted, each logged at info level by hash only. A folder left empty is removed (`remove_dir`, which never removes anything else). **That `fs::remove_file` in `media/trash.rs` is the only deletion of a user's media file in Rappel.** A backup that is pruned later no longer protects anything: it can no longer be restored.

**Export and backups are unchanged**: an export carries the `media` rows' files, so trashed files are not exported; backups copy only the database. A restored backup gets its files back from the trash as long as the purge kept them, which it does for every backup still in `backups/`.

**UI** (`dialogs/clean_up.rs`, `data/preferences_dialog.blp`, `data/clean_up_media_dialog.blp`). Preferences gets a **Storage** group with the row **Clean Up Media** whose subtitle is counted on a worker when the dialog opens ("Looking for files no card uses…", then "12 unused files, 4.3 MB" or "No unused files"; sizes by `g_format_size`, decimal as GNOME writes them), and a **Clean Up…** button, sensitive only with something to move and nothing running (the row activates it). The button asks **Clean Up Media?**: "12 media files that no card uses (4.3 MB) will move to the trash in Rappel's data folder. After 30 days they are deleted, except those a backup still uses." with Cancel (default) and **Clean Up** (destructive appearance: it removes files from the app, though reversibly). Then a toast "Moved 12 files (4.3 MB) to the trash" with Undo (none if nothing was left to move), and the row counts again. The texts and the button rule are pure functions with tests.

**Alert focus.** libadwaita 1.10 focuses an `AdwAlertDialog`'s default response in a large window but its *last* response in a small one (seen at 360 × 640 and 640 × 360), which is the destructive one: Enter or Space would have moved the files, and the same held for Delete Card, Start Fresh and Restore. This was observed with tests, not read: libadwaita's C source is not on this system, only its headers. Every alert loaded through `ui::dialog::Alert` now puts the focus on its default response once shown (`focus_default_when_shown`: `adw_dialog_set_focus` on the response's button in `map`, and again from an idle at `G_PRIORITY_HIGH`, which runs before GDK's input events at `G_PRIORITY_DEFAULT`, so a queued key never reaches the destructive button; a warning if the button is not found), tested at the three sizes.

## Consequences

- New: `Store::unused_media` (`UnusedMedia`), `Store::clean_up_media` (`CleanedUp`), `Store::undo_clean_up`, `Store::tidy_media_trash` (`TrashTidied`), `media::PURGE_AFTER_DAYS`, `Error::ClockWrong`. `Store::open` brings back the trashed files the database has rows for; `add_media` holds the write lock from naming to its row; card writes and imports bring back the files they name.
- A start with a non-empty trash lists it and looks up a row per file at open, and on a worker reads every card that names media (and, once a folder is old enough, every backup). For thousands of trashed files and a dozen backups of 20,000 cards this is a second or two on the worker, nothing on the window.
- A card with a reference typed or pasted by hand to a file that is only in the trash gets it back when the card is saved; one whose file was purged shows it as missing, as before.
- A trashed duplicate whose name is in the media folder again stays in the trash while the database uses it, and goes with its folder's purge afterwards.
- Leftover `.incoming-…` files from a crash are not cleaned up (they are not user data, but deleting anything else was not approved): they take space until removed by hand. Rare: a crash during an add.
- The toast "Moved … to the trash" is cut with "…" at 360 px, like other long toasts (phone pass, slice 6).

# 63. Untrusted input, round 3: images, audio, archives and the Anki import; batched syncs; time bounds

- Status: Accepted
- Date: 2026-10-19
- Amends: ADR 0054 (an import's apply syncs its new media files in batches before naming them), ADR 0025, ADR 0050 (rows 50 on of the untrusted-input table)
- Refers to: SPEC §4.1, §4.3, §4.9, §4.11, §4.10; `docs/briefs/phase-2.md` (slice 10); ADR 0062 (the GStreamer allow-list, found and fixed in the same slice)

## Context

Phase 2 added images (ADR 0055), audio (ADR 0056), media in the archive (ADR 0054), the streaming import (ADR 0053) and the Anki import (ADR 0061). Each came with its own hostile tests. This round, as rounds 1 and 2 did (ADR 0025, ADR 0050), writes the attacks the brief lists as tests first, runs them against the code as it was, fixes what fails, and records every attack with its result. It also takes the open items earlier slices left for it: the cost of syncing every media file of an import, time bounds that failed under load, two unexplained deaths of the app's test process, pasting a file that is neither an image nor audio, and the first audio play's wait.

## Decision

### Method

As ADR 0050: each attack is a test; a test that passes at once means the defence already held, and says so below; for every fix, its test was run against a scratch copy of the code with the fix reverted (`git archive` unpacked under `target/tmp`, never the working tree) and failed there. Time bounds are CPU time at the reference machine's speed (ADR 0049). Done for rows 50, 51, 62 and 72 (each test failed with its fix reverted: the huge PNG "reached the decoder", the process grew by over 900 MiB, the bomb was refused as too large instead of at its declared size, the cancelled plan used as much CPU as a whole one) and for ADR 0062's two fixes; row 55 is ADR 0062's. Every test of the "held" rows was run on the code before its round-3 fix, if any, and passed there.

### Batched syncs for an import's media (slice 10, item C1)

**Before:** an import's apply wrote each new media file to a temporary file, synced it (`fsync`), gave it its name, and synced the folder once at the end. Each `fsync` waits for a journal commit: 10,000 small files took **68 s** to apply, and 99,998 took over 17 minutes (measured in slice 2).

**Now** (`media::MediaBatch`): each file is copied into a temporary file and checked exactly as before (kind, cap, structure, hash), but not synced alone. When the batch holds 128 files (or 256 MiB), and at the end, its files are synced together on up to 64 threads, then each is named (`give_name`, unchanged), and at the end the folder is synced once. Parallel `fsync`s share journal commits: on this machine (ext4 on an SSD, debug build, a scratch data folder under `target/tmp`):

| 10,000 small files | Apply |
|---|---|
| Before (one `fsync` after another) | 68.2 s |
| 1 sync thread | 66.3 s |
| 8 threads | 16.0 s |
| 32 threads | 4.8 s |
| **64 threads (chosen)** | **2.9 s** |
| 128 threads | 2.0 s |
| No `fsync` at all (not kept, for comparison) | 1.0 s |

99,998 files now apply in **28.9 s**. A batch of 512 files is no faster than 128, and each pending file is an open file, so 128 keeps far from the usual limit of 1,024. 64 threads, each with a 64 KiB stack, only wait.

**Durability, the argument of ADR 0054 kept:** a media row commits only after its file's content and its name are on disk. A file is named only after its content is synced (the batch's sync comes before any of its names); every name is synced (the folder) before `finish` returns; `finish` returns before the transaction commits; any error drops the transaction. So after a crash at any point: no row without its file, and no media name with incomplete content, as before. What changes: a crash before the commit can leave up to one batch (128) of `.incoming-…` temporary files instead of one, which a clean-up leaves alone as before (ADR 0057); and an import that fails or is cancelled removes the files of the batch it has not named (`Drop`), where before every file copied stayed. Tests: `media::tests::a_batch_names_its_files_once_synced_and_leaves_no_temporary_file`, `a_failed_or_dropped_batch_removes_what_it_has_not_named`, and every import test (both formats). The speed itself is measured, not pinned by a test: a bound on the time spent waiting for a disk would fail on a slow one, and ADR 0049 times CPU only.

### Time bounds that failed under load (item C2)

`storage::tests::perf::a_card_with_a_long_log_is_fast` failed once at 6.09 s against 6 s, on its import, a single measurement. ADR 0049 divides a time over its bound by the slowdown of a reference measured right after it, but the reference does not slow down exactly as the work does (1.4 apart under heavy load), and a burst of load can fall on the work and not on the reference. Three ways were weighed: a larger slowdown factor (it weakens every bound for every run), bounds counted in operations (exact, but most bounds guard SQL plans and layout, which have no countable unit outside the code under test), and **measuring the work again** when it is over its bound. The last is chosen (`test_support::cpu_within_retried`, and the same in the app's `testing`): work that can be run again from the same state is measured up to three times, and the first verdict within the bound passes. A regression is slow every time, so it still fails; a burst during one run does not. Applied to the long log's import (into a new database each time) and to `review_page::tests::a_reveal_of_the_largest_backs_stays_cheap` (the reveal animated again); the other bounds already take the best of three runs (`fastest`). Checked under 40 busy loops on the 20-thread machine (load average over 25): `storage::tests::perf` 3 runs of 3 and the reveal and drop-down tests 5 runs of 5 passed. The drop-down test (`ui::dropdown::tests::the_factories_survive_new_labels_and_the_popup_stays_narrow`) was fixed in slice 6 (it waits for the popover to be mapped) and passed every run.

### Two unexplained deaths of the app's test process (item C3)

Not reproduced. `kernel.core_pattern` here hands cores to apport, which keeps none for a binary outside a package, so each run went under `gdb -batch` (backtraces of every thread on a signal) with 10 busy loops of load, the whole app test binary (`--test-threads=8`) per run. 29 runs ended: 26 passed whole, and none of the 29 died of a signal (gdb: "exited normally", or exit code 101 for failed tests). Runs 27 to 29 failed one to six image tests (`render::picture`), whose decodes did not end within their 60 s: the machine was then critically short of memory (7.9 GB of a 15 GB RAM in tmpfs and caches), which also made Claude Code stop the loop during run 30; glycin's loader processes are what memory pressure stalls first. Since slice 7 removed the locale race (tests keep the C locale and avoid libintl), 76 + 29 runs have shown no death. If one comes back, the same loop (a script under `target/tmp`, not kept) catches its backtrace.

### Pasting a file that is neither an image nor audio (item C4)

Pasting a copied text file or folder from Files showed "This file is not an image or audio file of a supported kind". GNOME Text Editor pastes such a file's path, which Files offers as text beside the file list. Now, when a paste or a drop of files adds none and every file was refused as not media of a supported kind (or not a file, a folder), the offer's text goes in instead, at the cursor or the drop point, as one undoable step (`media::text_instead`, pure); a paste uses the text view's own paste, a drop the text read with the files. A file refused for another reason (too large, damaged, unreadable, not on this computer) is still a refusal that says why, and so is a file list with no text. Tests: `dialogs::card_editor::media::tests::files_that_are_not_media_paste_as_their_text`, `insert::tests::files_that_are_not_media_go_in_as_their_text`.

### The first audio play's wait (item C5)

Solved by ADR 0062's registry of Rappel's own: the first play after an install or an update makes and starts the stream in 0.13 to 0.34 s on the main thread instead of 1.9 s. Warming it up earlier was not done: without a binding only a `GtkMediaFile` starts `GStreamer`, on the main thread just the same, and at every start for a card that may never play.

### Clean-up #3 (section D)

- **Shared:** the child-process runner of the app's tests (`testing::run_alone`, used by `ui_files`, `i18n`, `gst_env` and `audio_player`, which each had a copy); the byte readers of the media modules (`media::bytes`, used by the structure check, the image header reading and the colour profile walk); `test_support::set_hook` for every test hook.
- **Stale temporary files:** `.incoming-…` files a crash left in the media folder are removed by the trash's tidy at startup once a day old (`media::store::remove_stale_incoming`), never younger ones, which an add or an import may be writing; they are incomplete copies, never a media file.
- **Removed:** `media::ingest` and its `Sync` choice (only the imports used them; they use `MediaBatch`); stale "slice 5"/"slice 3" references in comments.
- **Left, and why:** files over 800 lines (`review_page.rs` 2,363, `browser_page.rs` 2,111, `card_editor/mod.rs` 1,348, `anki/import.rs` 1,300 and others): each is one page or one import with its tests; splitting them moves hundreds of lines without changing what they do, which this slice has no test of its own to justify, and a later slice touching them can split along what it changes. No `#[expect]` is unneeded (each would fail the build once fulfilled, ADR 0047), and there is no TODO or FIXME.
- **ARCHITECTURE.md:** every file and identifier it names exists (checked by listing them against the tree); the modules of this slice are added.

## Consequences

- An import with many media files applies tens of times faster; nothing else changes for the user.
- Images are shown without their colour profile, as sRGB.
- An archive entry is refused as soon as it gives more than it declares, so a deflate bomb costs what it declares, not the limit.
- Test hooks are set through `test_support::set_hook`, whose guard clears them when dropped, even if the test panics (slice 9's follow-up).
- `rusqlite`'s `hooks` feature is on (no new crate); it makes `Store` larger, so `AfterReset::Opened` boxes it (`clippy::large_enum_variant`).
